# Corbits Codex OAuth with a cloud Interchange hub

Checked 2026-09-28. Implemented path: keep `@corbits/codex-provider` for inference and token mapping, and use a **device-code login** for sign-in from a browser on any machine. The small Hub route uses `@corbits/oauth-core` for code exchange, encrypted credential persistence, and renewal. Interchange core remains unchanged. A live account sign-in still needs verification; the published packages do not supply the device flow themselves.

| Approach | Validation | Verdict |
| --- | --- | --- |
| Current `@corbits/oauth-core/hub` browser login | [`mountOAuthLogin`](https://github.com/corbitsdev/corbits-oauth-core/blob/main/src/hub/mount.ts) starts a callback listener inside the hub; [`startCallbackServer`](https://github.com/corbitsdev/corbits-oauth-core/blob/main/src/callback-server.ts) binds loopback only. [`codexOAuthConfig`](https://github.com/corbitsdev/corbits-codex-provider/blob/main/src/constants.ts) fixes the redirect to `http://localhost:1455/auth/callback`. A browser on another machine sends that redirect to *its own* localhost. | Works when browser and listener share a host; does not complete a normal cloud-hub/browser login. |
| Codex device code | [OpenAI recommends it for remote/headless login](https://learn.chatgpt.com/docs/auth#login-on-headless-devices); the [Codex implementation](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs) obtains a user code, polls, then exchanges the returned code with a device callback URI. No localhost listener is involved. Personal/workspace settings must enable it. | **Choose this** for a browser client and cloud hub. Add a narrow Corbits device-login path; reuse its encrypted credential persistence and refresher. Validate with the target account, since device login can be disabled. |
| SSH port forward | [OpenAI documents](https://learn.chatgpt.com/docs/auth#fallback-forward-the-localhost-callback-over-ssh) `ssh -L 1455:localhost:1455` for the fixed callback. | Useful operator bootstrap, not a normal web-client sign-in. |
| Local OAuth and credential import | The [Corbits root API](https://github.com/corbitsdev/corbits-oauth-core/blob/main/README.md) can sign in locally and the hub can store `oauth_token` credentials. | Would require a secure token handoff and put refresh tokens on the client; reserve as a fallback, not the product flow. |

The relevant current Corbits sources, [`@corbits/oauth-core` 0.2.0](https://github.com/corbitsdev/corbits-oauth-core/blob/main/package.json), [`@corbits/codex-provider` 0.1.1](https://github.com/corbitsdev/corbits-codex-provider/blob/main/package.json), and [`@corbits/mcp`](https://github.com/corbitsdev/corbits-mcp/blob/main/README.md), document browser PKCE/loopback or MCP OAuth discovery; I found no Codex device-code or hosted-redirect implementation in their source/exports. A hosted HTTPS callback also cannot simply replace Codex's fixed registered localhost redirect. The Codex [live inference test](https://github.com/corbitsdev/corbits-codex-provider/blob/main/e2e/live.test.ts) is opt-in and does not prove cloud OAuth.

The checkout now resolves published npm releases: `@corbits/codex-provider` 0.1.1, `@corbits/credential-http` 0.1.0, and `@corbits/oauth-core`, `@corbits/mcp`, `@corbits/mailbox`, and `@corbits/openai-responses` 0.2.0. Registry versions were checked on 2026-09-28 and installed with Bun; the lockfile contains npm registry entries rather than GitHub pins. `@corbits/credential-http` is an optional peer of the published MCP package but is required by its hub export. The device route is in `interchange/apps/hub/src/codex-device-login.ts`; it replaces the loopback login in this app, while retaining the Corbits refresher. Changing package versions alone would not have removed the loopback limitation.

For the cloud connection, serve this Vite client and the hub's `/api` under one HTTPS origin, as the client already makes relative `/api` requests with same-origin cookies (`src/lib/hub.ts`, `vite.config.ts`). Set Better Auth's public base URL to that origin (`interchange/packages/hub-api/src/auth.ts`). Separately, verify that the cloud Interchange composition has a sidecar provisioner and the Codex adapter: the checked-in default composition cannot deploy workflows (`interchange/README.md`, `interchange/DEV.md`). These are deployment prerequisites, independent of the Codex login change.

Local proof on 2026-09-28: the Hub booted against the existing PostgreSQL database; the chat client signed in through the same-origin `/api` proxy; and the protected device-login route rejected an anonymous call with 401. Device authorization completed with the intended ChatGPT account, a Codex credential was stored and shared with the tenant, and a deployed Interchange agent returned real streamed replies. The client build and lint and Interchange's `make all` passed. The local test harness supplies the sidecar provisioner; it is not a production deployment.

Proof still needed: verify credential renewal when the token expires and run the client, Hub, and provisioned sidecar behind a public HTTPS origin. No cloud instance URL exists yet, so cloud routing remains unverified.
